# IoT-Messenger Wire Protocol (v1)

Единый контракт обмена данными между микроконтроллером (firmware/), релей-сервером (server/) и клиентским приложением (web-app/).
Протокол спроектирован с учетом жестких ограничений ОЗУ на ESP8266: плоский JSON, короткие имена ключей, максимальный размер пакета — 1024 байта.

---

## 1. Транспорт и авторизация

### 1.1 Облачный режим (WebSocket — основной)
* Endpoint устройства (ESP): wss://<HOST>/ws?role=dev&token=<DEVICE_TOKEN>
* Endpoint клиента (App/Web): wss://<HOST>/ws?role=usr&token=<DEVICE_TOKEN>
* При успешном подключении сервер отправляет пакет status с состоянием собеседника (online / offline).

### 1.2 Локальный режим без интернета (LAN / mDNS)
* ESP поднимает локальный WebSocket-сервер на порту 81 и анонсирует себя по mDNS как _iotbot._tcp.local.
* Клиент подключается напрямую по адресу ws://<DEVICE_IP>:81/ws?token=<DEVICE_TOKEN> и использует те же самые JSON-пакеты, что и через облачный релей.

### 1.3 HTTP Fallback (для редкой отправки с батарейных плат)
* POST /api/v1/msg с заголовком Authorization: Bearer <DEVICE_TOKEN> и телом в виде стандартного JSON-пакета msg.

---

## 2. Формат JSON-пакетов

Все сообщения передаются в кодировке UTF-8. Неиспользуемые поля опускаются для экономии памяти ESP.

### 2.1 Текстовое сообщение и инлайн-кнопки (type: "msg")
Отправляется как от устройства (from: "dev"), так и от пользователя (from: "usr").

{
  "v": 1,
  "type": "msg",
  "id": "m_1042",
  "from": "dev",
  "ts": 1794905120,
  "text": "Температура в теплице: 24.5°C",
  "edit": false,
  "kb": [
    [
      { "t": "Включить полив", "d": "pump_on" },
      { "t": "Обновить", "d": "status" }
    ],
    [
      { "t": "Перезагрузить ESP", "d": "reboot" }
    ]
  ]
}
Описание полей:
* v *(int, req)* — версия протокола (1).
* type *(string, req)* — тип пакета ("msg", "cb", "status", "ping", "pong", "err").
* id *(string, req)* — уникальный ID сообщения (ESP может передавать счетчик или millis(), сервер при необходимости дополняет префиксом).
* from *(string, req)* — отправитель: "dev" (плата) или "usr" (телефон).
* ts *(int, opt)* — Unix timestamp в секундах. Если ESP шлет 0, сервер подставляет текущее время.
* text *(string, req)* — текст сообщения или команда (например, "/start"). Лимит: до 512 байт.
* edit *(bool, opt)* — если true, клиент обновляет текст и кнопки существующего сообщения с таким же id вместо создания нового (удобно для живых показателей датчиков).
* kb *(array, opt)* — двумерный массив инлайн-кнопок (ряды -> кнопки). Максимум 3 ряда по 3 кнопки:
  * t *(string)* — текст на кнопке (label).
  * d *(string)* — строка callback_data, которая вернется на ESP при нажатии.

### 2.2 Нажатие на инлайн-кнопку (type: "cb")
Отправляется клиентом при нажатии на кнопку под сообщением устройства.

{
  "v": 1,
  "type": "cb",
  "id": "m_1042",
  "from": "usr",
  "d": "pump_on"
}
### 2.3 Статус онлайн/офлайн (type: "status")
Генерируется сервером при подключении или обрыве связи устройства.

{
  "v": 1,
  "type": "status",
  "dev_online": true,
  "last_seen": 1794905125
}
### 2.4 Heartbeat (ping / pong) и ошибки (err)
* ESP отправляет {"v":1,"type":"ping"} каждые 25 секунд.
* Сервер отвечает {"v":1,"type":"pong"}. Если ответа нет 5 секунд — ESP разрывает сокет и переподключается с паузой 3 секунды.
* Ошибка от сервера:
  {"v":1,"type":"err","code":401,"msg":"Invalid token"}
  Коды: 400 (битый JSON), 401 (неверный токен), 413 (пакет больше 1024 байт), 429 (превышен лимит сообщений).

---

## 3. Логика хранения и Push-уведомлений на релее
1. Сервер хранит последние 50 сообщений для каждого DEVICE_TOKEN в SQLite, чтобы при открытии приложения пользователь видел историю событий.
2. Если приходит пакет type: "msg" от from: "dev", а активных WebSocket-клиентов role=usr для этого токена сейчас нет, сервер отправляет Web Push уведомление с текстом из поля text.

## 4. REST API

Все ответы — JSON в кодировке UTF-8. Ошибки возвращаются тем же пакетом `err`, что и в WebSocket (§2.4), например: `{"v":1,"type":"err","code":401,"msg":"Invalid token"}`.

### 4.1. История сообщений
`GET /api/v1/history?token=<DEVICE_TOKEN>&limit=50`
* `token` *(req)* — токен устройства.
* `limit` *(opt)* — сколько последних сообщений вернуть, от 1 до 50 (по умолчанию 50).

Ответ `200`:
```json
{
  "messages": [
    {
      "v": 1,
      "type": "msg",
      "id": "m_1042",
      "from": "dev",
      "ts": 1794905120,
      "text": "Температура в теплице: 24.5°C",
      "kb": [[{ "t": "Обновить", "d": "status" }]]
    }
  ]
}
```
Массив упорядочен по возрастанию `ts` (от старых к новым). Необязательные поля (`edit`, `kb`) опускаются.

### 4.2. Создание устройства
`POST /api/v1/devices/create`

Ответ `201`:
```json
{ "token": "DEVICE_TOKEN" }
```
Если на сервере задан `ADMIN_KEY`, запрос обязан содержать заголовок `Authorization: Bearer <ADMIN_KEY>`.

### 4.3. HTTP Fallback отправки сообщения
`POST /api/v1/msg` с заголовком `Authorization: Bearer <DEVICE_TOKEN>` и телом — стандартным пакетом `msg` (§2.1) от `from: "dev"`.

Ответ `202`:
```json
{ "ok": true }
```

### 4.4. Проверка доступности релея
`GET /api/v1/health`

Ответ `200`:
```json
{ "ok": true, "v": 1, "uptime": 3600 }
```
`uptime` — число секунд с момента запуска сервера. Используется PWA-клиентом для проверки адреса релея в мастере настройки.
